# Payment Processor

Асинхронный сервис процессинга платежей на `FastAPI + PostgreSQL + RabbitMQ`.

## Что реализовано

- `POST /api/v1/payments` c `Idempotency-Key`
- `GET /api/v1/payments/{payment_id}`
- статический API key через заголовок `X-API-Key`
- outbox pattern для гарантированной публикации событий
- асинхронный consumer на `FastStream`
- эмуляция платежного шлюза: задержка 2-5 секунд, успех 90%, ошибка 10%
- максимум 3 начатые попытки доставки webhook с задержками `1s -> 2s` и общим счётчиком в БД
- резервирование доставки с ограниченным сроком и восстановлением после падения consumer
- DLQ `payments.dlq` для окончательно упавших сообщений
- Alembic миграции
- Docker Compose окружение

## Архитектура

1. API создаёт запись в `payments` и событие в `outbox` в одной транзакции.
2. Dispatcher в процессе API публикует outbox в `payments.new`. После подтверждения RabbitMQ он отмечает запись опубликованной. При сбое повторяет попытку с backoff до 30 секунд.
3. Consumer блокирует строку платежа, один раз эмулирует шлюз и резервирует попытку webhook в БД. HTTP выполняется после commit, без удержания блокировки строки.
4. Успешная доставка фиксируется в БД. При ошибке сохраняются причина, число начатых попыток и время следующей попытки.
5. Повтор публикуется в отдельную очередь с фиксированным TTL: по умолчанию `payments.retry.1000ms` или `payments.retry.2000ms`. Quorum-очереди с at-least-once dead-lettering возвращают сообщения в `payments.new` с подтверждением доставки.
6. После исчерпания попыток consumer публикует сообщение в `payments.dlq` и сохраняет терминальное состояние доставки. Повторные исходные сообщения не запускают отправку заново.
7. Исходное сообщение подтверждается только после завершения обработки или подтверждённой публикации retry/DLQ. Сбои PostgreSQL/RabbitMQ приводят к requeue с паузой, некорректные события — к DLQ.


## Запуск

```bash
cp .env.example .env
make up
```

Остановить стек:

```bash
make down
```

Полезные команды:

```bash
make help
make logs
make ps
make migrate
make clean
```

Сервисы после запуска:

- API: `http://localhost:8000`
- PostgreSQL: `localhost:5433`
- Swagger UI: `http://localhost:8000/docs` только при `DOCS_ENABLED=true` (режим разработки)
- RabbitMQ UI: `http://localhost:15672` (`guest` / `guest`)

## Примеры запросов

Создание платежа:

```bash
curl -X POST http://localhost:8000/api/v1/payments \
  -H "Content-Type: application/json" \
  -H "X-API-Key: super-secret-key" \
  -H "Idempotency-Key: order-1001" \
  -d '{
    "amount": "1500.00",
    "currency": "RUB",
    "description": "Оплата заказа #1001",
    "metadata": {
      "order_id": "1001",
      "customer_id": "cust-1"
    },
    "webhook_url": "https://httpbin.org/post"
  }'
```

Получение статуса платежа:

```bash
curl http://localhost:8000/api/v1/payments/<payment_id> \
  -H "X-API-Key: super-secret-key"
```

## Переменные окружения

- `API_KEY` - ключ для всех HTTP эндпоинтов
- `DATABASE_URL` - async SQLAlchemy DSN
- `RABBITMQ_URL` - DSN для RabbitMQ
- `OUTBOX_POLL_INTERVAL_SECONDS` - интервал опроса outbox
- `OUTBOX_BATCH_SIZE` - размер пачки публикации
- `PAYMENT_SUCCESS_RATE` - вероятность успешного платежа
- `PAYMENT_DELAY_MIN_SECONDS` / `PAYMENT_DELAY_MAX_SECONDS` - диапазон задержки шлюза
- `RETRY_MAX_ATTEMPTS` - максимум попыток доставки webhook
- `RETRY_BASE_DELAY_SECONDS` - базовая задержка для backoff
- `WEBHOOK_TIMEOUT_SECONDS` - общий deadline HTTP-запроса и timeout отдельных операций
- `WEBHOOK_LEASE_SECONDS` - срок резерва попытки; должен быть больше HTTP deadline (по умолчанию 30 секунд)
- `DOCS_ENABLED` - включает публичные `/docs`, `/redoc`, `/openapi.json` для разработки; по умолчанию выключен

Некорректные диапазоны задержек, вероятности, размеров пачки и числа попыток отклоняются при старте. `RETRY_MAX_ATTEMPTS` допускает значения от 1 до 10. Параметры API и consumer должны совпадать.

## Идемпотентность и доставка

- `Idempotency-Key` обязателен, содержит от 1 до 255 символов и не может состоять только из пробелов. Конкурентные запросы возвращают один платёж. Повтор с другим телом также возвращает исходный платёж — сравнение тел не выполняется.
- Outbox обеспечивает at-least-once публикацию: сбой после publish и до commit может создать дубль. Статус обработанного платежа при повторе не пересчитывается.
- `webhook_attempts` считает начатые попытки, включая успешные и прерванные падением процесса. Инфраструктурный сбой до резервирования попытки не расходует лимит.
- При падении consumer исходное сообщение остаётся неподтверждённым. Следующая обработка ждёт истечения резерва; результат старого владельца после смены резерва отвергается. Если последняя попытка прервана, исход доставки может быть неизвестен и событие уйдёт в DLQ.
- Webhook передаёт стабильный заголовок `X-Webhook-ID`, равный `payment_id`. Получатель должен сохранять обработанные идентификаторы и возвращать 2xx для повторов. Падение после успешного HTTP и до записи результата в БД может привести к повторной доставке. Гарантия не означает успешную доставку при постоянно недоступном получателе: действует лимит попыток.
- DLQ также может содержать дубли, если процесс упал после публикации и до записи её результата. Для корректных событий используется стабильный AMQP `message_id` вида `<payment_id>:dlq`. Для некорректного JSON сохраняются причина ошибки и исходные байты в `original_body_base64`.
- Повторная публикация сообщения из DLQ сама по себе не сбрасывает терминальное состояние или бюджет попыток. Автоматического redrive в этом сервисе нет.

## Проверка состояния

```bash
curl -H "X-API-Key: super-secret-key" http://localhost:8000/health/ready
```

Ответ `200` означает, что задача dispatcher работает без зарегистрированной ошибки последнего прохода; `503` — задача отсутствует, завершилась или выполняет восстановление после ошибки. Это проверка dispatcher, а не подтверждение доставки каждого webhook. Ошибки публикации и обработки пишутся в логи.

## Обновление существующего окружения

Миграция `20261023_0002` добавляет состояние доставки и переводит `webhook_attempts` из количества ошибок в количество попыток: у ранее доставленных платежей добавляется успешная попытка. Историю прерванных отправок восстановить нельзя.

На время обновления остановите API и consumer, примените `alembic upgrade head` и запустите оба процесса новой версии. В Compose миграция запускается сервисом `migrate` до старта приложений. Старую очередь `payments.retry` можно оставить до её опустошения: она возвращает сообщения в прежнюю `payments.new`.

RabbitMQ использует именованный volume `rabbitmq_data` и hostname `payment-rabbitmq`; обычные остановка и пересоздание контейнера сохраняют очереди. При переходе со старого Compose сначала перенесите существующие данные брокера и сохраните исходное имя узла: новый volume не подключит прежнее хранилище автоматически. `make clean` удаляет volumes и предназначен для полного сброса данных.

## Тесты

Локальные проверки:

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -e '.[test]'
make test
```

Интеграционные тесты используют отдельные PostgreSQL и RabbitMQ на портах `15433` и `15673`, базу `payment_test` и Compose-проект `payment-processor-tests`:

```bash
make test-integration
```

Тесты настоящего перезапуска PostgreSQL/RabbitMQ и пересоздания контейнера брокера:

```bash
make test-containers
```

Они затрагивают только тестовый Compose-проект. Не запускайте их одновременно с другими интеграционными тестами. Таблицы `payments` и `outbox` в тестовой БД очищаются между сценариями. Для отдельного тестового окружения можно задать `TEST_DATABASE_URL` (имя БД должно оканчиваться на `_test`) и `TEST_RABBITMQ_URL`; проверки контейнеров используют стандартный локальный стек.

```bash
make test-down
```

Проверяются конкурентная идемпотентность, блокировка дублей, восстановление резерва, стабильный результат платежа, три попытки и DLQ, ошибки записи результата и публикации retry/DLQ, некорректные сообщения, независимые TTL-очереди, миграции и восстановление dispatcher.
