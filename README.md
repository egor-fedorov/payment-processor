# Payment Processor

Тестовое задание: асинхронная обработка платежей на Python 3.14, FastAPI,
PostgreSQL, SQLAlchemy и RabbitMQ/FastStream. Сервис принимает платёж,
возвращает `202`, эмулирует шлюз (2–5 секунд, вероятность успеха 90%) и
отправляет результат на webhook. Повторный запрос с тем же ключом возвращает
исходный платёж, в том числе при конкурентном создании.

## Быстрый старт

Нужны Docker и Docker Compose v2:

```bash
cp .env.example .env
make up
```

Compose применяет миграции, затем запускает API, отдельный dispatcher и
consumer. API доступен на `http://localhost:8000`, RabbitMQ UI — на
`http://localhost:15672` (`guest` / `guest`). Порты опубликованы только на
loopback. `make down` сохраняет данные в именованных volumes.

```bash
curl -s http://localhost:8000/api/v1/payments \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: super-secret-key' \
  -H 'Idempotency-Key: order-1001' \
  -d '{"amount":"1500.00","currency":"RUB","description":"Заказ 1001",
       "metadata":{"order_id":"1001"},
       "webhook_url":"https://example.com/payment-hook"}'

curl -s http://localhost:8000/api/v1/payments/<payment_id> \
  -H 'X-API-Key: super-secret-key'
```

Замените `webhook_url` адресом своего HTTP-получателя. Полностью локальная
демонстрация с получателем включена в `make benchmark`.

`Idempotency-Key` обязателен: 1–255 символов, не только пробелы. При повторе
с другим телом возвращается первоначальный платёж. Поддерживаются `RUB`,
`USD`, `EUR`; сумма положительная, не более 12 цифр и 2 знаков после точки.
Защита бизнес-эндпоинтов — статический `X-API-Key`. Swagger и OpenAPI по
умолчанию выключены; для разработки задайте `DOCS_ENABLED=true`.

## Архитектура и гарантии

```text
HTTP → API → PostgreSQL: payments + outbox (одна транзакция)
                         ↓
                     dispatcher → RabbitMQ payments.new → consumer
                         ↑                                  ↓
                  retry / recovery / DLQ             шлюз → webhook
                         ↑                                  ↓
                         └──────── PostgreSQL ───────────────┘
```

- `app/domain.py` — значения и команды; `app/contracts.py` — форматы событий.
  HTTP-схемы преобразуются в команды, сервисы не зависят от FastAPI.
- `app/services` — создание платежа, обработка, интерфейсы шлюза, часов и
  webhook-клиента. `app/db` — ORM, сессии и операции с хранилищем.
- `create_app()` и `create_worker()` собирают зависимости. API создаёт ресурсы
  в lifespan; consumer использует один HTTP-клиент с пулом соединений.
- Dispatcher резервирует готовые записи через `FOR UPDATE SKIP LOCKED`,
  освобождает транзакцию, публикует с publisher confirms, затем сохраняет
  результат. Реплики разделяют работу. Истёкшие резервы можно забрать снова.
- Consumer резервирует обработку вместе с отложенным recovery-событием.
  Эмуляция шлюза и HTTP выполняются вне транзакции. Перед HTTP попытка
  записывается в БД; результат может сохранить только действующий владелец
  резерва. Результат эмуляции стабилен для `payment_id`, включая повтор после
  аварии до сохранения статуса.
- Ошибка HTTP атомарно сохраняет причину и новое событие в outbox с
  `available_at`. По умолчанию максимум **3 начатые отправки**, задержки между
  ними — 1 и 2 секунды. После исчерпания бюджета там же создаётся DLQ-событие.
  Retry, recovery и DLQ не требуют отдельных TTL-очередей.
- ACK допустим после сохранения результата или будущей работы в БД. Дубли
  активной обработки безопасно подтверждаются: восстановление уже записано.
  Ошибка инфраструктуры приводит к requeue с паузой. Некорректное сообщение
  сохраняется для DLQ с причиной и исходными байтами в Base64.

Доставка **at least once**. Сбой после publish и до фиксации в БД может
дублировать AMQP-событие; его `message_id` остаётся ID outbox-записи. Сбой после
HTTP 2xx и до записи результата может повторить webhook. Получатель должен
дедуплицировать стабильный `X-Webhook-ID`, равный `payment_id`. Если последняя
начатая отправка оборвалась, её исход может остаться неизвестным: после
истечения резерва платёж попадёт в DLQ. Повторное сообщение не сбрасывает
счётчик и терминальное состояние; автоматического redrive нет.

Сроки резервирования требуют синхронизированных часов между процессами.
Lease больше максимальной задержки шлюза и HTTP deadline, но остановка
процесса дольше lease всё равно допускает повтор внешнего вызова. Для реального
платёжного провайдера потребуется его собственная идемпотентность.

## Масштабирование и настройки

```bash
docker compose up -d --scale consumer=2 --scale dispatcher=2
```

| Настройка | По умолчанию | Назначение |
|---|---:|---|
| `CONSUMER_CONCURRENCY` | 16 | RabbitMQ prefetch и лимит HTTP-соединений на consumer |
| `DATABASE_POOL_SIZE` | 10 | Максимум соединений каждого процесса; overflow выключен |
| `DATABASE_POOL_TIMEOUT_SECONDS` | 5 | Ожидание свободного соединения |
| `OUTBOX_PUBLISH_CONCURRENCY` | 8 | Одновременные публикации dispatcher |
| `OUTBOX_BATCH_SIZE` | 50 | Дополнительный верхний предел выборки |
| `OUTBOX_POLL_INTERVAL_SECONDS` | 1 | Пауза при отсутствии готовой работы |
| `OUTBOX_PUBLISH_TIMEOUT_SECONDS` / `OUTBOX_LEASE_SECONDS` | 10 / 30 | Deadline публикации и срок её резерва |
| `OUTBOX_RETENTION_HOURS` | 24 | Хранение опубликованных событий |
| `WEBHOOK_TIMEOUT_SECONDS` / `WEBHOOK_LEASE_SECONDS` | 5 / 30 | Общий HTTP deadline и срок обработки |
| `RETRY_MAX_ATTEMPTS` / `RETRY_BASE_DELAY_SECONDS` | 3 / 1 | Бюджет отправок и экспоненциальная задержка |

Пулы нужно учитывать суммарно: `(API + consumers + dispatchers) × pool_size`,
плюс миграции и административные соединения. Частичный индекс outbox содержит
только неопубликованные записи. Опубликованная история удаляется порциями до
1000 строк раз в минуту. Платежи автоматически не удаляются.

Полный набор параметров — в `.env.example` и `Settings`. Ошибочные интервалы,
вероятности и размеры отклоняются при запуске. `DATABASE_URL` и `RABBITMQ_URL`
используются при запуске Python-процессов напрямую; Compose задаёт адреса
сервисов внутри своей сети. Для внешних зависимостей нужен Compose override.
Все consumer-реплики должны использовать одинаковые настройки retry/lease.

Это демонстрация ограниченной конкурентности, коротких транзакций и
восстановления. Одиночные PostgreSQL/RabbitMQ в Compose не обеспечивают HA;
webhook URL предполагается доверенным. Rate limiting, управление секретами,
защита исходящих запросов и реальные платежи выходят за рамки задания.

## Разработка и проверки

Нужен `uv 0.13.5`; Python 3.14.9 закреплён в `.python-version`.

```bash
make install                 # uv sync --locked
make check                   # lockfile, Ruff, форматирование, strict mypy, unit tests
make format                  # исправления Ruff и форматирование
uv run --locked pre-commit install
make test-all                # все тесты и coverage с учётом ветвлений >= 90%
make test-down
```

Зависимости приложения и разработки зафиксированы в `uv.lock`. CI выполняет
те же проверки, интеграционные сценарии с настоящими PostgreSQL/RabbitMQ,
сборку образа и smoke-тест всего пути до webhook. Runtime-образ использует
непривилегированного пользователя, не содержит dev-зависимостей и собирается
из lockfile. GitHub Actions закреплены по commit SHA.

Тестовый Compose-проект `payment-processor-tests` публикует PostgreSQL на
`15433`, AMQP на `15673`, management API на `15674`. Каждый pytest-запуск
создаёт случайную БД и RabbitMQ vhost и удаляет их в teardown; `.env` не
используется как источник тестовых подключений. Есть отдельные команды
`make test-integration` и `make test-containers`. Последняя перезапускает
только выделенные тестовые контейнеры; её нельзя выполнять одновременно
с другим запуском на этом стенде.

Проверяются конкурентная идемпотентность, стабильный статус, бюджет retry,
атомарность планирования, истечение и смена владельца lease, отсутствие
DB-блокировки во время сетевого ожидания, разделение outbox между репликами,
ошибки БД/брокера, HTTP deadline, сохранность очереди и восстановление после
SIGKILL consumer. При создании тестовой БД выполняются `alembic upgrade head`
и `alembic check`.

Для внешнего тестового стенда доступны `TEST_DATABASE_URL`,
`TEST_RABBITMQ_URL`, `TEST_RABBITMQ_MANAGEMENT_URL`. PostgreSQL-пользователю
нужно право создания БД, RabbitMQ-пользователю — управления vhost. Контейнерные
сценарии рассчитаны на локальный тестовый Compose.

## Диагностика и benchmark

`GET /health/live` проверяет жизнь API без авторизации. `GET /health/ready`
с `X-API-Key` выполняет ограниченный по времени `SELECT 1` и возвращает
`200` или `503`. Готовность API не означает доступность RabbitMQ: входящие
платежи могут накапливаться в outbox во время восстановления брокера.

Приложение пишет JSON-логи с `request_id`, `payment_id`, `event_id`, номером
попытки и длительностью соответствующей операции. API возвращает
`X-Request-ID`. Состояние webhook доступно через GET платежа; размер очередей
— через RabbitMQ UI. Готовый backlog outbox можно проверить SQL-запросом:

```sql
SELECT count(*), min(available_at)
FROM outbox
WHERE published_at IS NULL AND available_at <= now();
```

```bash
make build
make benchmark
# быстрый smoke-test без задержки эмулятора:
uv run --locked python benchmarks/run.py --payments 4 --replicas 1 --gateway-min 0 --gateway-max 0
```

Benchmark запускает собственный Compose-проект, локальный webhook-получатель
и свободные порты. Сравнивает 1 и 2 consumer, каждый с concurrency=4:
прогрев, затем 40 платежей, задержка шлюза 2–5 секунд. Измеряет throughput,
p50/p95/p99 HTTP POST и времени до webhook, проверяет число доставок и пустой
outbox. После завершения удаляет только собственный проект и его volumes.
Результат с параметрами и данными окружения — `reports/benchmark.json`.
Это локальное сравнение масштабирования, без заявленного production SLA.

Пример измерения от 2026-10-23 (`dc89937`): Linux x86_64, 20 логических CPU,
Python 3.14.9; параметры по умолчанию, по 40 платежей после прогрева.

| Consumer-реплик | Время до всех webhook | Платежей/с | POST p95 | До webhook p95 |
|---:|---:|---:|---:|---:|
| 1 | 37,46 с | 1,068 | 83,98 мс | 34,39 с |
| 2 | 19,73 с | 2,028 | 100,16 мс | 18,21 с |

В обоих прогонах — 40 доставок, 40 отправок, нулевой остаток outbox.
Получен рост throughput примерно в 1,9 раза. Это один локальный прогон;
задержка эмулятора случайная, абсолютные значения зависят от окружения.
[Полные результаты с p50/p95/p99](benchmarks/results/local-2026-10-23.json).

Новый стек рассчитан на чистое развёртывание. Миграции сохраняют историю
схемы, но перенос живых старых TTL-очередей и данных RabbitMQ 3.x в 4.x
не является частью этого обновления.
